OVERVIEW:
The master_schema is the foundation layer of the entire booking system.
Everything else (fare calculation, booking engine, routes, quotas) references 
these tables. If master data is wrong, the entire booking system produces 
garbage results.

This schema answers the question:
"What stations exist, what trains run between them, on which days, with what 
coaches and seat quotas available for booking?"

BUSINESS RULES:

- Arrival time at station N+1 must be chronologically after departure from station N

- Day number must be non-decreasing throughout the route
- Origin station: arrival_time = NULL, departure_time = NOT NULL
- Destination station: arrival_time = NOT NULL, departure_time = NULL
- No duplicate station codes in the same route (train shouldn't stop twice at same station)
- Distance between any two adjacent stations > 0 km
- Changing one station's timing may require cascade adjustment of subsequent stations
- If train runs on specific days, all route stations inherit that schedule
- Booking quota at a station cannot exceed total seats for that class
- Commercial stops are the only stations where passengers can board/deboard
- Technical halts do not appear in passenger-facing search results
- Major junctions get higher booking quota allocation
- Day offset handles multi-day journeys (e.g., departure day 1, arrival day 2)

--------------------------------------------------------------------

├── General Quota: 180 (83%)
├── Tatkal Quota: 20 (9%)
├── Premium Tatkal Quota: 10 (5%)
├── Ladies Quota: 6 (3%)

BUSINESS RULES:
- Sum of all quotas must NOT exceed total_seats
- RAC limit ≤ 25% of total_seats
- Waiting list limit ≤ 2× RAC limit
- Lower berth quota is part of general quota (not additional)
- Different trains can have different quota distributions
- Seasonal/holiday templates override permanent ones based on effective dates
- Changing template does NOT affect already-booked tickets
- effective_to = NULL means template is permanent
- Only one active template per train per class at any given date
- Quotas can be station-specific via routes.booking_quota field
- Railway staff quota often zero (handled separately via passes)
- Emergency quota released to general pool before chart preparation
- Premium Tatkal quota is subset of Tatkal quota (not additional)

BUSINESS RULES:
- Sum of all coaches across all classes + EOG + PC = trains.total_coaches
- Coach numbering follows Indian Railway conventions:
  • H = First AC (1A)
  • A = Second AC (2A)
  • B = Third AC (3A)
  • S = Sleeper (SL)
  • C = AC Chair Car (CC)
  • E = Executive Chair Car (EC)
  • D = Second Sitting (2S)
  • GS/GN = General
  • PC = Pantry Car
  • EOG = Generator Car/End on Generator
- Coach position determines where it appears on platform display
- Can add temporary coaches during peak season (seasonal_addition = true)
- Coach IDs must be unique within a train composition
- Disabled-friendly coach (usually B1 or S1) must be marked
- Changing composition requires recalculating total seat availability
- effective_to = NULL means this composition is current
- EOG and PC are not passenger coaches (excluded from quota calculation)
- Coach position from engine helps in platform coach indication display
- Only one active composition per train per class at any date

→ INSERT INTO trains (references origin_station_code, destination_station_code)

STEP 3: Employee links Coach Types to Train
→ INSERT INTO train_coach_composition (references train_number, coach_class)

STEP 4: Employee defines Seat Availability Template
→ INSERT INTO seat_availability_templates (references train_number, coach_class)

STEP 5: Employee defines the Route
→ INSERT INTO routes (references train_number, station_code)
→ Multiple inserts for each stop in the journey

STEP 6: Booking System uses all this data:
→ User searches: SELECT trains + routes WHERE station_from and station_to exist
→ System checks: SELECT seat_availability_templates for quota availability
→ System calculates fare: base_fare × fare_multiplier (from coach_types and trains)
→ System displays: train details, route, available classes, fares to user

================================================================================
VALIDATION RULES (Cross-Table)
================================================================================

1. A route's station_code must exist in stations table
2. A route's train_number must exist in trains table
3. Route origin station must match train's origin_station_code
4. Route destination station must match train's destination_station_code
5. Sum of route distances must equal train's total_distance
6. Number of route stops must equal train's intermediate_stops_count + 2 (origin + destination)
7. Seat availability template's coach_class must exist in train_coach_composition for that train
8. Total seats in template = coach_types.seats_per_coach × train_coach_composition.number_of_coaches
9. Train status = 'Active' required for booking availability
10. Station status = 'Active' required to appear in search

OVERVIEW:
The fare_schema defines ALL pricing-related configurations for the booking system.
This is a FIXED fare system - NOT dynamic/surge pricing like flights or buses.

PHILOSOPHY:
- Fares are set by authorized employees (Fare Manager role)
- Once set, fares remain fixed until manually updated by an employee
- Different train types have DIFFERENT base fare rates (not same as Sleeper)
- Fare is calculated based on: distance slab × train type rate × class multiplier
- Final fare is always rounded to nearest ₹5 or ₹10 (Indian Railways standard)
- Low-cost trains (MEMU, Passenger) have very low fares, often in multiples of ₹5

EXAMPLE:
- MEMU local train: 10km = ₹5, 20km = ₹10, 30km = ₹15
- Passenger train: 10km = ₹10, 20km = ₹15, 30km = ₹20
- Express train: 10km = ₹20, 20km = ₹35, 30km = ₹45
- Superfast train: Express fare + surcharge
- Rajdhani: Premium fixed rate per km

This schema answers:
"How much does it cost to travel from Station A to Station B on Train T in Class C?"

- There is NO single "base fare" that all trains derive from

- Minimum fare ensures short-distance premium train travel still costs enough
- Distance slabs can vary by train type (different granularity for local vs express)
- per_km_rate_beyond is used when distance exceeds the last defined slab
- Fare change requires approval workflow if increase > 10%
- Historical fares preserved via effective_from/effective_to dates
- Only one active fare per train_type + coach_class + distance slab at any date

================================================================================
FARE CALCULATION WORKFLOW
================================================================================

HOW AN EMPLOYEE SETS FARES:

STEP 1: Employee opens "Fare Management" in Admin Panel
STEP 2: Selects Train Type (e.g., Express)
STEP 3: Selects Coach Class (e.g., Sleeper/SL)
STEP 4: Defines distance slab (e.g., 1-10 km)
STEP 5: Enters base fare amount (e.g., ₹20.00)
STEP 6: Sets minimum fare (e.g., ₹30.00)
STEP 7: Sets per km rate beyond slab (e.g., ₹2.00/km)
STEP 8: Repeat for all slabs, all classes, all train types

This is a MANUAL data entry process. The employee literally types in amounts.
There is NO auto-calculation from a single base rate.

---

HOW THE SYSTEM CALCULATES FARE DURING BOOKING:

Given: Journey from NDLS to CNB (435 km), Train 12309 (Rajdhani), Class 2A

STEP 1: Find base fare slab
→ Query base_fare_matrix WHERE train_type='Rajdhani' AND coach_class='2A' 
  AND 435 BETWEEN distance_from_km AND distance_to_km
→ Result: Slab 431-440 km, base_fare = ₹1,450.00

STEP 2: Add fare components
→ Reservation Charge: +₹40.00
→ Superfast Surcharge: +₹45.00 (if Superfast, but Rajdhani is not Superfast, skip)
→ Catering Charge: +₹100.00 (for Rajdhani)
→ Subtotal: ₹1,450 + 40 + 100 = ₹1,590.00

STEP 3: Apply concessions (if any)
→ No concession selected
→ Subtotal: ₹1,590.00

STEP 4: Apply adjustments
→ No special adjustment applicable
→ Subtotal: ₹1,590.00

STEP 5: Apply seasonal surcharge
→ Current date: 2024-10-28 (Diwali season)
→ Diwali Peak surcharge: 15% on base fare = ₹1,450 × 15% = ₹217.50
→ Subtotal: ₹1,590.00 + ₹217.50 = ₹1,807.50

STEP 6: Calculate GST (5% on total)
→ GST = ₹1,807.50 × 5% = ₹90.375 → rounded to ₹90.38
→ Fare before convenience fee: ₹1,807.50 + ₹90.38 = ₹1,897.88
→ Rounded to nearest ₹5: ₹1,900.00 (or ₹1,895.00 depending on rule)

STEP 7: Add convenience fee
→ Online + UPI + AC class = ₹35.00
→ GST on convenience: ₹35 × 18% = ₹6.30
→ Total convenience: ₹41.30

STEP 8: FINAL FARE
→ ₹1,900.00 + ₹41.30 = ₹1,941.30
→ Display to user: ₹1,941.30 (or rounded)

FARE BREAKUP DISPLAY:
--------------------------------------------------------------------
Base Fare (435 km, Rajdhani, 2A)        ₹1,450.00
Reservation Charge                        ₹40.00
Catering Charge                          ₹100.00
Diwali Peak Surcharge (15%)              ₹217.50
GST (5%)                                  ₹90.38
Subtotal (rounded)                      ₹1,900.00
Convenience Fee                           ₹35.00
GST on Convenience (18%)                   ₹6.30
─────────────────────────────────────────────────
TOTAL                                    ₹1,941.30

OVERVIEW:
The booking_config_schema is the RULE ENGINE for the entire booking system.
It defines WHEN, WHO, HOW MANY, and UNDER WHAT CONDITIONS a user can book tickets.

This schema answers the question:
"Is this booking allowed? What restrictions apply? What happens after booking?"

Every single booking request passes through these rules for validation before
the actual booking is created in bharat_railway_core.

KEY PRINCIPLE:
- All tables are PURE CONFIGURATION (set by admin employees)
- Booking engine READS these rules but NEVER writes to them
- Changes take effect for new bookings only (not retroactive)
- These are business rules, not transaction data

FOREIGN KEYS: quota_code → quota_definitions(quota_code)
              coach_class → master_schema.coach_types(coach_code)

ALLOCATION RULE ENUM VALUES:
- SEQUENTIAL: Fill quota 1 completely, then quota 2, then quota 3
- RATIO: Maintain ratio (e.g., 80% GN, 10% TQ, 5% LD, etc.)
- FILL_FIRST: Fill the most restricted quota first (e.g., Ladies first)

SPILLOVER ACTION ENUM VALUES:
- NEXT_QUOTA: Excess goes to next quota in sequence
- WAITLIST: Create waitlist ticket
- BLOCK: Stop accepting bookings

BUSINESS RULES:
- Priority 1 gets allocated first, then 2, then 3...
- FILL_FIRST: Reserved quotas filled before general
- RATIO: Maintains proportion between quotas (used for Tatkal+General)
- SEQUENTIAL: Complete fill one quota then move to next
- Spillover to WAITLIST only for General Quota (others go to NEXT_QUOTA)
- Auto-upgrade only from 3A→2A, SL→3A (not 2A→1A)
- Auto-upgrade is FREE (passenger doesn't pay extra)
- Berth preference: Seniors get lower berths first, then disabled, then females
- Family/group bookings: system tries to allocate adjacent berths
- Quota allocation priority can differ by train type

================================================================================
BOOKING VALIDATION FLOW (Complete)
================================================================================

When a user clicks "Book Now", the system runs ALL these validations:

STEP 1: CHECK BOOKING WINDOW
→ Query booking_window_rules
→ Is current date within advance_booking_days?
→ Is current time after booking_opens_time?
→ Is current time before (departure - booking_closes_hours_before)?
→ Result: ALLOW or BLOCK with message

STEP 2: CHECK USER RESTRICTIONS
→ Query booking_restrictions for this user
→ Count user's bookings this month < max_tickets_per_month?
→ Count user's bookings today < max_tickets_per_day?
→ For Tatkal: count today < max_tatkal_per_day?
→ Is journey distance > min_distance_for_class?
→ Any IP rate limit exceeded?
→ Result: ALLOW or BLOCK with violation_message

STEP 3: CHECK PASSENGER VALIDITY
→ Query passenger_rules
→ Age validation (infant, child, adult, senior)
→ ID proof validation (required? acceptable type?)
→ Gender rules (ladies quota only for females)
→ Nationality rules (foreign tourist quota)
→ Result: VALID or REJECT with reason

STEP 4: ALLOCATE SEATS
→ Query quota_definitions + quota_allocation_priority
→ Determine applicable quotas based on booking
→ Allocate in priority order
→ Apply berth preferences
→ Check waitlist_config for RAC/WL limits
→ Result: CONFIRMED / RAC / WAITLIST / NO AVAILABILITY

STEP 5: BOOKING CREATED (in core DB)
→ Wait for chart preparation (chart_preparation_rules)
→ Chart prepared at specified hours before departure
→ WL auto-cancelled, RAC upgraded if applicable

STEP 6: POST-BOOKING OPERATIONS
→ Modification: check modification_rules
→ Cancellation: check refund_rules + fare_schema.cancellation_charges
→ Process refund according to refund_rules

================================================================================
CORE DESIGN PRINCIPLES
================================================================================

1. ROLE-BASED ACCESS CONTROL (RBAC):
   - Employees are assigned ROLES
   - Roles have PERMISSIONS
   - Permissions define what actions are allowed
   - Employee CANNOT have direct permissions (only through roles)

2. STATION SCOPE:
   - Some roles are station-specific (Station Master)
   - Others are system-wide (Fare Manager, Super Admin)
   - employee_station_assignments defines station scope

3. HIERARCHY:
   - Employees have reporting managers
   - Approval workflows use this hierarchy
   - Fare changes > 10% need manager approval

4. AUDIT TRAIL:
   - Every employee action logged (see audit_schema)
   - Employee ID tracked in all config changes

ROLE HIERARCHY:
Level 1 (Highest): Super Admin → Full system access, no restrictions
Level 2: Zone Head → Manage entire zone (e.g., Northern Railway)
Level 3: Division Head / Fare Manager / Refund Manager → Division level + approvals
Level 4: Station Master / Route Designer / Train Controller → Operational roles
Level 5 (Lowest): Auditor / Support Staff → View access or limited scope

BUSINESS RULES:
- System roles (is_system_role=true) cannot be deleted, only deactivated
- Role level determines approval hierarchy (lower level needs higher level approval)
- Station-scoped roles can only manage their assigned stations
- Session timeout: FINANCE roles = 10 min, others = 15 min
- Max login sessions: prevents credential sharing
- Role code is permanent (used in code, not role_name which can change)
- New custom roles can be created by SUPER_ADMIN
- Roles can be deactivated (no new assignments) without deleting

================================================================================
AUTHORIZATION FLOW
================================================================================

When an employee logs in and performs an action:

STEP 1: AUTHENTICATION (via bharat_railway_core)
→ Employee logs in with credentials
→ System verifies employee exists, is active, not locked
→ JWT token issued with employee_id

STEP 2: LOAD PERMISSIONS
→ Get employee's roles from employee_roles (via assigned roles)
→ Get permissions from employee_role_permissions for those roles
→ Build permission set: {STATION_CREATE, STATION_READ, FARE_READ, ...}

STEP 3: CHECK STATION SCOPE (if applicable)
→ Get assigned stations from employee_station_assignments
→ If station-scoped role: limit data access to assigned stations only

STEP 4: AUTHORIZE ACTION
→ Employee clicks "Update Fare"
→ System checks: does permission set contain FARE_UPDATE?
→ YES: Allow action
→ NO: Return 403 Forbidden

STEP 5: CHECK APPROVAL REQUIREMENT
→ If permission.requires_approval = true
→ And fare change > employee.max_fare_change_percent
→ Then: Create approval request for higher authority
→ Else: Execute directly

STEP 6: AUDIT LOGGING
→ Action logged in audit_schema with employee_id, action, timestamp

3. Check fare_change_approvals: Approval chain shows Zone Head approved

5. Check change_reference: "MOR/FARE/2024/REV-003"

Result: Change was legitimate, properly approved, with documented authority.
Audit PASSED ✓

SCENARIO 2: SCAM INVESTIGATION (CBI/ED RAID)
--------------------------------------------------------------------
Question: "Was fare deliberately increased before Diwali to extract extra money?"

Query:
1. Search config_change_log for fare changes in October (Diwali month)
2. Cross-reference with seasonal_surcharges active during same period
3. Check if fare increase + seasonal surcharge was excessive
4. Trace who approved, when, with what justification
5. Check if same employee made unusual changes elsewhere
6. Cross-reference employee_action_log for suspicious login patterns

Result: If fare was increased 50% + 15% Diwali surcharge = 65% total,
and approval was bypassed (emergency flag), and employee logged in 
from unusual IP at midnight → PRIMA FACIE EVIDENCE OF FRAUD

1. Find employees who created new stations recently

3. Cross-reference with booking data in core DB
4. Trace employee's login patterns (unusual hours? different IP?)
5. Check if employee accessed refund/payment modules
6. Look for PERMISSION_DENIED events (probing for access)

Result: Employee created 5 fake stations, assigned routes, 
attempted to access refund module (PERMISSION_DENIED logged) → 
EVIDENCE OF ATTEMPTED FRAUD

5. Trace IP address (office or external?)
6. Check config_change_log for any permission changes before export

personal IP address, role doesn't permit export → DATA BREACH CONFIRMED

SYSTEM INTEGRITY FEATURES
================================================================================

1. DIGITAL SIGNATURES:
   - Every config_change_log record has SHA256 hash
   - Daily verification job recalculates and compares hashes
   - Any mismatch → audit_tamper_log entry created
   - Hash includes: log_id + timestamp + employee_id + old_value + new_value

2. SEQUENCE MONITORING:
   - log_sequence is a BIGSERIAL (no gaps in normal operation)
   - Daily job checks for gaps in sequence
   - Gaps indicate possible record deletion
   - Gap alerts logged in audit_tamper_log

3. IMMUTABLE STORAGE:
   - Audit tables on separate tablespace
   - No UPDATE or DELETE grants to any user (including Super Admin)
   - Only INSERT allowed
   - "Deletion" is soft (marked as deleted but record retained)

4. REAL-TIME ALERTS:
   - Critical changes trigger email/SMS to Super Admin
   - Suspicious activity triggers security team alert
   - Tamper detection triggers system-wide notification

5. EXTERNAL VERIFICATION:
   - Daily audit report generated with checksums
   - Can be verified by external auditor without DB access
   - Blockchain anchoring for critical records (future)

    Cr. Unearned Revenue            ₹1,500

    Cr. Other Income                ₹190

BUSINESS RULES:

- Ticket fare deferred until chart preparation (service not yet provided)

- No revenue recognized on waitlisted tickets (uncertain outcome)
- RAC tickets: 50% recognized, 50% deferred (partial service)
- Revenue recognized NET of GST (not including GST collected)
- Changes to rules require Finance Head approval
